Scope: engineering research and a proposed validation plan. **No docking, folding, minimization, benchmark, installation, model-weight download, sequence submission, or service execution was performed.** Reading public documentation/source text is the only computational work represented here. Recommendation: use **local HADDOCK3 as a provisional baseline for linear, canonical L-peptides with an explicitly justified TNF surface hypothesis**, conditional on an actual platform and scientific pilot. These are engineering judgments, not results of a comparative run.

## 1. Which engines are defensible and engineerable?

### Takeaway

These engines have peptide-specific methods; a generic small-molecule docking interface is insufficient evidence of peptide-folding support. HADDOCK3 provides the clearest documented route to a configurable local lab, including peptide ensembles, restraints, explicit flexibility, seeds and analysis. Its installation and TNF performance remain untested here. — [HADDOCK peptide best practices](https://www.bonvinlab.org/software/bpg/peptides/), [HADDOCK3 peptide example](https://github.com/haddocking/haddock3/blob/d67d8a597568bb6ab498747c86416c7257ab9736/examples/docking-protein-peptide/docking-protein-peptide-full.cfg).

#### HADDOCK: construction, restraints, platform and licensing

- The official HADDOCK3 tutorial constructs helix, extended/strand and polyproline-II peptide conformers using PyMOL `fab`; these are initial hypotheses, not experimentally established free-peptide structures. It describes active/passive ambiguous interaction restraints (AIRs), and reports a complete example taking about **2 h 11 min on an M2 using eight cores**. This is an author-reported tutorial example, not a TNF runtime estimate or a run on this machine. — [Official local protein–peptide tutorial](https://www.bonvinlab.org/education/HADDOCK3/HADDOCK3-protein-peptide/).
- The pinned full example uses `topoaa → rigidbody → seletop → flexref → emref → clustering/selection`, with a three-conformation 11-residue peptide, 3,000 rigid-body samples and selection of 400 for refinement. It explicitly defines the peptide segment with `fle_sta_1`, `fle_end_1`, `fle_seg_1`, and increased refinement steps. This is a useful recipe to adapt, not an automatically validated TNF configuration. — [Pinned full configuration](https://github.com/haddocking/haddock3/blob/d67d8a597568bb6ab498747c86416c7257ab9736/examples/docking-protein-peptide/docking-protein-peptide-full.cfg).
- The current installation documentation is headed **2026.10.1** and describes bundled CNS executable troubleshooting. Python package availability does not prove that the CNS binary works on a particular architecture. The manual provides Docker and Apptainer routes; those do not establish native ARM support or equivalent performance by themselves. Standard CNS stages use CPU resources; no GPU is required by the proposed recipe. — [Installation](https://www.bonvinlab.org/haddock3/pages/INSTALL.html), [CNS installation](https://www.bonvinlab.org/haddock3-user-manual/install-cns.html), [Docker](https://www.bonvinlab.org/haddock3-user-manual/docker-install.html), [Apptainer](https://www.bonvinlab.org/haddock3-user-manual/usage-container.html), [CPU execution configuration](https://github.com/haddocking/haddock3/blob/d67d8a597568bb6ab498747c86416c7257ab9736/src/haddock/modules/defaults.yaml).
- HADDOCK3 code has an Apache-2.0 license, but the standard topology/docking/refinement modules depend on **CNS**, which has separate nonprofit/commercial terms. The disclaimer specifically lists `topoaa`, `rigidbody`, `flexref`, `emref` and `mdref`. Do not describe the complete dependency stack as unconditionally Apache licensed. The older HADDOCK distribution is obtained through a nonprofit/noncommercial license form. — [HADDOCK3 repository/license](https://github.com/haddocking/haddock3), [CNS disclaimer](https://github.com/haddocking/haddock3/blob/d67d8a597568bb6ab498747c86416c7257ab9736/DISCLAIMER.md), [2.x access](https://www.bonvinlab.org/software/haddock2.4/download/).
- **Cyclic peptides:** HADDOCK2.4 has a published two-stage cyclization/docking protocol. HADDOCK3 documents pre-cyclization distance restraints followed by topology regeneration with `cyclicpept`, `cyclicpept_dist` or `disulphide_dist`. Ring closure, the exact bond topology and the conformer ensemble must be checked; arbitrary staples/linkers are not silently covered. — [Primary cyclic-peptide paper](https://doi.org/10.1021/acs.jctc.2c00075), [HADDOCK3 cyclic-building instructions](https://www.bonvinlab.org/haddock3-user-manual/docking_scenarios/cyclic-peptides.html).
- **D residues:** HADDOCK3's FAQ explicitly says chirality is read from the input coordinates while residues retain the corresponding L-residue names. It recommends zeroing `mdsteps_rigid` and `mdsteps_cool1` in `flexref` for this case. Thus a one-letter sequence alone is not a complete D-peptide specification; validate stereocentres after building, topology generation and refinement. Do not assume this exact behavior for every historical 2.x installation. — [Official D-amino-acid note](https://www.bonvinlab.org/haddock3-user-manual/faq.html).

#### Rosetta: scope and chemistry boundaries

- FlexPepDock refinement expects a reasonably placed starting peptide; the documentation discusses about 5 Å initial backbone RMSD. Ab-initio mode still needs initial proximity to the binding pocket. Benchmarks described there use 5–15-residue peptides; PIPER-FlexPepDock is particularly suited to approximately 6–12 residues. Standard FlexPepDock largely assumes a stable receptor backbone; optional receptor-backbone minimization in the global workflow is not extensive receptor conformational sampling. — [FlexPepDock documentation](https://docs.rosettacommons.org/docs/latest/application_documentation/docking/flex-pep-dock).
- PIPER-FlexPepDock's primary paper separately evaluates bound and unbound receptor conformations and uses fragment generation, global PIPER placement, refinement and clustering. Its parallel CPU examples do not imply laptop-scale runtimes. The fragment database/search tools and PIPER executable need their own pinned inputs and access checks. — [Primary PIPER-FlexPepDock paper](https://journals.plos.org/ploscompbiol/article?id=10.1371/journal.pcbi.1005905).
- Rosetta is free under its noncommercial license for eligible academic/nonprofit/government use; commercial access requires the relevant paid license. Published GitHub source is not an unrestricted open-source license. The current download page links source, precompiled releases, a Docker image and ROSIE; exact image architecture and FlexPepDock executable availability remain pilot gates. — [Current downloads and terms](https://rosettacommons.org/software/download/), [licensing explanation](https://rosettacommons.org/software/licensing-faq/).
- Rosetta supports D-residue machinery, including explicit noncanonical design configuration, but that does not establish every FlexPepDock centroid/fragment stage as D-compatible. `simple_cycpep_predict` explicitly builds closed peptides with L/D mixtures and optional crosslinks; it is a **conformer-building protocol**, not evidence that unmodified FlexPepDock correctly docks all such chemistries. Ring-preserving moves, params/patches, scoring and stereochemistry require a dedicated validated protocol. — [D-residue documentation](https://docs.rosettacommons.org/docs/latest/rosetta_basics/non_protein_residues/D-Amino-Acids), [cyclic-peptide builder](https://docs.rosettacommons.org/docs/latest/structure_prediction/simple_cycpep_predict).

#### ADCP: current-version correction and limits

- The official homepage directs users to **v1.1/FUGU**. v1.1 adds nonstandard side-chain libraries, explicit D chirality, all-atom pose output and optional OpenMM minimization. Its sequence syntax uses `&` to mark D chirality; **lowercase letters are not a D-residue convention**. In the original method, letter case selected initial extended versus helical conformations. — [v1.1 overview](https://ccsb.scripps.edu/adcpv11/), [original ADCP method](https://pmc.ncbi.nlm.nih.gov/articles/PMC6954657/).
- Current downloads say **Linux only**, using a Python 3.7 environment; an official linked Mac route uses Ubuntu in a UTM VM on M1/M2. The older ADFRsuite macOS x86-64/Python 2.7 package is not evidence of a native Apple Silicon v1.1 installation. Treat VM architecture, pinned dependency resolution and realistic CPU/memory use as gates. No official ready-to-use container or native macOS v1.1 execution was verified here. — [v1.1 downloads](https://ccsb.scripps.edu/adcpv11/downloads/), [older ADFRsuite downloads](https://ccsb.scripps.edu/adfr/downloads/).
- v1.1 documentation is explicitly under construction. It describes affinity-map preparation and box definition, and examples with modified/D residues. OpenMM ranking can differ from docking-score ranking; `-dr` retains docking-score ordering and `-reint` changes the OpenMM energy expression. Some nonstandard-residue parameter sets require SwissSideChain licensing. Box restriction is a spatial prior, not equivalent to HADDOCK AIRs. — [v1.1 documentation](https://ccsb.scripps.edu/adcpv11/documentation/).
- Backbone-cyclic and disulfide-cyclic options are documented in the older source/tutorial (`-cyc`, `-cys`). That is evidence for those specific ADCP protocols, not arbitrary thioether/stapled chemistries or a guarantee of unchanged v1.1 behavior. Verify current flags, ring closure and any minimizer's bond treatment before admitting cyclic inputs. — [Older driver](https://github.com/ccsb-scripps/ADCP/blob/1c1a330a9eec846c801f771542c4f2c88d0351e5/runADCP.py), [cyclic tutorial](https://ccsb.scripps.edu/adcp/tutorial-cyclic/).
- The public older repository carries a GNU Library GPL v2 license file; this alone does **not** settle every component of the packaged v1.1 suite or parameter libraries. Capture the actual distribution notices before use or redistribution. Older documentation recommends substantial replica/Monte Carlo sampling; tiny tutorial runs are usage demonstrations, not convergence evidence. — [Repository license](https://github.com/ccsb-scripps/ADCP/blob/1c1a330a9eec846c801f771542c4f2c88d0351e5/COPYING.LESSER), [sampling guidance](https://ccsb.scripps.edu/adcp/documentation/).

### Inferences

- **Baseline proposal:** start with linear canonical L-peptides, an experimentally justified TNF patch, multiple idealized conformers, local CPU HADDOCK3 and an explicit fully flexible peptide. Keep the receptor's flexible region and restraint assumptions visible. Use the shipped small test configuration for a later installation smoke test, then the peptide benchmark below. The full example is not a smoke test, and a successful process exit is not scientific validation.
- **Orthogonal proposal:** independently dock the same small positive/control panel with ADCP v1.1 in its verified Linux/VM environment, initially keeping optional OpenMM postprocessing separate. Match the receptor state and site prior. Agreement in pose/contact family is useful robustness evidence; numerical score agreement is meaningless across different scoring functions. Disagreement triggers review rather than averaging scores.
- Keep the adapter capability manifest conservative: `linear_L` may become supported after pilot; `D`, `head_to_tail_cycle`, `disulfide_cycle`, `N_methyl`, caps and custom linkers each need their own tested path. Reject unknown chemistry explicitly. These engines dock/model structures; none of the above establishes that a generated sequence binds TNF.
- Scoring failure modes to test: a missed pose from insufficient sampling; a native-like pose sampled but ranked poorly; receptor-state or protonation error; restraint-driven circular recovery; excessive electrostatic/size preference; invalid peptide geometry or ring closure; and unmodeled receptor motion. Ranking failure and sampling failure must be reported separately.

### Gaps

- No engine has passed a local pilot, runtime/resource limit, seed-repeatability test or TNF benchmark in this work. No engine is yet an accepted dependency of the lab.
- HADDOCK3/CNS binary compatibility, actual version/commit, dependency terms and any container digest must be verified in the selected environment. The documented M2 example makes a native attempt defensible; it does not prove readiness on this Mac.
- PIPER local distribution/licensing and current server operation were not settled. FlexPepDock/PIPER server fetches timed out; that is not proof of permanent unavailability. No server job was created.
- ADCP v1.1 packaged license composition, explicit seeded replay and current cyclic behavior remain gates. Its published Linux/VM path is documented, not executed. GPU acceleration for optional OpenMM was not verified; do not budget the core docking workflow on assumed GPU speedups.

## 2. What benchmark and scientific gates should precede TNF design claims?

### Takeaway

Bound redocking, unbound crossdocking and de novo candidate assessment answer different questions. A whole-Fab pose recovery is a useful antibody/coordinate pipeline check, but cannot validate short-peptide sampling, chemistry, score discrimination or TNF binding. The proposed lab should report receptor-aligned peptide errors, contacts, clusters and controls before presenting ranked designs. — [PIPER bound/unbound evaluation](https://journals.plos.org/ploscompbiol/article?id=10.1371/journal.pcbi.1005905), [3WD5 experimental identity](https://www.rcsb.org/structure/3WD5), [DockQ definitions](https://github.com/wallnerlab/DockQ).

### Cited Findings

- 3WD5 is the experimental **TNF–adalimumab Fab** complex. Its deposited components include TNF and antibody H/L chains, not a short isolated peptide binder. A CDR segment cut out of this Fab would change the ligand and remove its scaffold; the complex does not experimentally establish that the excised sequence binds by itself. The last sentence is an inference from the deposited molecular identities, not an assay result. — [RCSB 3WD5](https://www.rcsb.org/structure/3WD5).
- HADDOCK's peptide guidance recommends multiple starting conformations, increased refinement sampling and RMSD clustering rather than assuming the protein–protein defaults are optimal. The public 1NX1 example supplies a peptide sequence, receptor and bound reference, making it a traceable initial technical fixture. — [Peptide best practices](https://www.bonvinlab.org/software/bpg/peptides/), [1NX1 example assets](https://github.com/haddocking/haddock3/tree/d67d8a597568bb6ab498747c86416c7257ab9736/examples/docking-protein-peptide).
- DockQ exposes ligand RMSD, interface RMSD, fraction of recovered native contacts and clash information, and supports explicit chain mapping. Its README explicitly warns that the scalar DockQ score cannot be trusted under `--capri_peptide`; do not silently apply the usual protein–protein DockQ quality bins to that mode. Use the underlying metrics and record the implementation/version. — [DockQ README](https://github.com/wallnerlab/DockQ/blob/master/README.md).
- DockQ offers a peptide-specific evaluation mode. The lab must pin the actual contact/interface cutoffs from its selected version rather than rely on a generic “DockQ” label; percentages calculated at different cutoffs are not directly comparable. — [DockQ mode documentation](https://github.com/wallnerlab/DockQ/blob/master/README.md), [version-specific constants to retain](https://github.com/wallnerlab/DockQ/blob/master/src/DockQ/constants.py).

### Inferences

The following is a **proposed acceptance plan**, not a claim that these tests or thresholds were executed or validated for TNF.

#### Benchmark tracks

| Track | Inputs and question | Required limit on interpretation |
|---|---|---|
| Bound-coordinate placement/refinement | Extract receptor and peptide from a solved peptide complex; perturb translation/rotation and optionally backbone by recorded amounts. Can the pipeline recover the pose near the known site? | Retaining the bound backbone makes this an easier diagnostic. Report it explicitly. |
| Bound-receptor peptide folding/docking | Use the bound receptor but build peptide ensembles from sequence without its experimental coordinates. | Tests peptide search in a favorable receptor conformation. Native-derived restraints/box must be labeled as information supplied. |
| Unbound crossdocking | Use an independently determined apo receptor, or a receptor from another complex, with exact sequence/construct mapping; independently build the peptide ensemble. | Measures receptor-state transfer. Do not call a receptor extracted from the same complex “unbound.” |
| Whole-Fab control | Keep H/L together as the experimentally associated Fab and dock against the declared TNF model. | Protein–protein/antibody control only. It cannot replace either peptide track. |
| Prospective TNF candidates | Use the frozen recipe, justified receptor state and predefined site hypothesis. | Without a solved peptide pose, no true pose RMSD/contact recovery can be calculated. Report model hypotheses and uncertainty. |

#### Measurements

1. Define residue/atom mappings before analysis: author versus label chains, insertion codes, missing residues, alternate locations, occupancy filtering, termini, caps and protonation. Superpose the predicted receptor onto the reference using a fixed common receptor backbone/core mask. Apply that one rigid transform to the whole predicted complex.
2. Report **receptor-aligned peptide backbone RMSD** on common `N, CA, C, O` atoms, in Å, **without refitting the peptide**. Add a Cα-only value only if labeled. An independently fitted peptide RMSD measures internal conformation and can conceal a wrong binding site.
3. Distinguish canonical **interface RMSD** (the interface atoms are fitted according to the chosen CAPRI/DockQ implementation) from a separately named **receptor-frame interface RMSD**. Report the fitting mask and interface definition for both. Never use a receptor-dominated whole-complex RMSD as the main peptide quality metric.
4. Define native heavy-atom residue-pair contacts at a preregistered cutoff; **4 Å is proposed for this peptide panel**, to be checked against the pinned evaluator. Report `Fnat = recovered native pairs / native pairs`, plus predicted-contact precision, nonnative contacts and severe clashes. If 5 Å or 4.5 Å is also useful, report it as a separate sensitivity analysis.
5. Handle TNF symmetry deliberately: specify the mature construct, oligomeric state, allowed equivalent protomer mappings and whether contacts span a protomer boundary. Report symmetry-equivalent mappings transparently. A single-protomer simplification is a separate model; inspect candidate clashes against the intended trimer/neighbor context. Do not assume that a deposited assembly label automatically supplies all biological/symmetry neighbors.
6. Cluster in the receptor frame by peptide backbone RMSD and/or contact fingerprint. Record cutoff, atom set, algorithm, cluster size, representative selection and contributing seeds. Report top-1/top-5/top-10 **cluster representative** recovery, alongside the best sampled pose. The latter diagnoses sampling; the former diagnoses ranking. RMSD to the best-scoring model is convergence to a model, not accuracy against experiment.

#### Controls and baseline

- **Technical positive:** begin with a deposited short-peptide complex such as the official 1NX1 fixture, then at least one second unrelated peptide complex and a matched bound/unbound receptor pair. Freeze benchmark identities before tuning; avoid testing only systems used to choose settings.
- **TNF positive:** require a literature-supported TNF-binding peptide with exact sequence, chemical form and a direct binding measurement under recorded conditions. If no solved complex exists, use it for score/control discrimination, not pose-accuracy claims. Adalimumab/Fab can be a separate TNF protein positive; it cannot fill the peptide-positive slot. No particular TNF peptide is certified as this positive by this engine review.
- **Negatives:** include experimentally documented nonbinders if available. Also include several length/composition/charge-matched scrambled sequences, a conservative presumed interface-disrupting variant and an unrelated target/surface control. Scrambles and designed mutations are **putative decoys**, not experimentally proven negatives. Use identical preparation, site priors, budgets and rank selection; report the full distribution rather than one favorable comparison.
- **Simple baseline:** score/minimize the input conformer ensemble and a fixed, reproducibly generated set of random site placements under the same geometry filters. Compare whether full docking improves native-pose retrieval and ranking over that baseline. Include the native complex's rescoring as a diagnostic only; do not insert the native pose into blind candidate selection. Keep score-only, local-refinement and broader-search outcomes distinct.
- **No circular validation:** a box centered on the crystal peptide or AIRs extracted from that exact interface define an informed benchmark. Label it accordingly. Keep a separate broader/withheld-restraint test before claiming binding-site discovery. The same information budget must apply to both engines and controls.

#### Admission gates

1. **Environment gate:** verify the selected license/use context and exact CPU architecture; pin engine revision, CNS/builder versions and container/environment identity. Run a tiny public fixture later with bounded cores, memory, disk and wall time; require complete models, intact residues and informative failure handling.
2. **Reproducibility gate:** repeat an explicit seed in a pinned environment and compare coordinates/terms within stated tolerances; then run at least three independent seeds. Capture actual per-job seeds and parallelism. Fixed seeds alone do not guarantee byte-identical results across hardware/libraries. Reject runs with silent residue loss or topology changes.
3. **Geometry gate:** verify sequence, stereochemistry, peptide bonds, termini/caps, bond lengths/angles, clashes and backbone outliers. For cyclic/D inputs, separately demonstrate bond closure and chirality preservation through every stage. Start those branches only after a canonical-peptide pipeline is working.
4. **Scientific pilot gate:** predeclare a practical pilot criterion, for example a top-10 cluster representative with receptor-aligned peptide backbone RMSD ≤2.5 Å and Fnat ≥0.5 in at least two of three seeds on the small held-out short-peptide panel. This is an **engineering admission criterion**, not a universal CAPRI standard or proof of binder discovery. Report individual outcomes and failure cases. If only bound tests pass, restrict claims to the demonstrated bound/refinement setting; do not present unbound TNF discovery as validated.
5. **TNF gate:** verify receptor context and independently justified restraints; compare the TNF peptide positive and controls under the frozen protocol. Absence of an adequate positive/negative panel leaves TNF ranking uncalibrated even if generic pose benchmarks pass. Orthogonal docking can reveal sensitivity but cannot substitute for a direct binding assay and a separate functional assay.

#### Provenance to retain for every future run

Store accession and source URL; exact downloaded bytes' SHA-256 and UTC retrieval; PDB/mmCIF revision; construct/chain/residue mapping; oligomer/assembly/symmetry transformation; omitted atoms/residues; occupancy/altloc policy; peptide sequence **and explicit chemistry**; generated starting conformers and builder/version; receptor preparation/protonation; every restraint and its evidence category; grid centre/size/spacing for ADCP; full expanded engine configuration, code/build/database/parameter versions, licenses, seed list, thread count, hardware, OS/container digest, resource limits, elapsed time, logs, all retained poses, stage scores, cluster assignments, evaluation scripts/version and reference hashes. For a predictor additionally save weights revision/license, templates, alignments, recycles/samples and confidence arrays. Missing provenance should lower reproducibility status rather than be reconstructed from memory.

### Gaps

- This review does not select or verify a TNF-binding short-peptide assay/control panel, an apo TNF structure, or a peptide-bound TNF reference. Those are scientific input gates, not grounds to manufacture a benchmark from a Fab fragment.
- Neither docking score separation nor contact recovery establishes affinity, specificity, neutralization, cellular effects or clinical efficacy. Scores can favor attractive but nonbinding decoys, and native-like pose recovery alone does not validate sequence ranking. The initial lab should offer structural hypotheses, not measured Kd/IC50 claims.
- No outcome table, success rate, timing for TNF, convergence plot or cross-engine agreement result exists from this work.

## 3. What is verified about LocalFold, and where could prediction help?

### Takeaway

LocalFold is an **optional prediction/prototyping candidate**, not the docking baseline. Its repository makes a genuine in-browser inference claim and contains CPU/WebGPU model implementation directories; that is stronger documentation than merely a local-looking UI, but it is **not executed verification** of a selected model, its numerical fidelity, privacy behavior, chemistry handling or TNF peptide performance. — [Official linked repository](https://github.com/sokrypton/localfold), [pinned source tree](https://github.com/sokrypton/localfold/tree/0724b7fcebd9a83d263d9d9c485f818dce0242a1).

### Cited Findings

- **User-observed UI, not independently exercised here:** the page offered AF3, OpenBind-0, OpenDDE, Boltz-2, Protenix-v2, Mol-1, IntelliFold-2, RoseTTAFold3, AF2 monomer/multimer, ESMFold2 and BioEmu2, with a footer claiming local folding and MMseqs2-server MSA. The user reported no sequence submission and no Fold click. These are observations supplied in this chat about [localfold.org](https://localfold.org), not an audit of every backend. ### Inferences

- A complex predictor can later supply an **alternative starting pose or conformer hypothesis** for canonical peptides and the specified TNF assembly. It should be judged by the same chemistry, geometry, receptor-frame and control panel as docking. Keep template-assisted and template-free results separate, and record training/template leakage risks for old PDB benchmarks.
- Predictions sharing templates, training data or closely related architectures are not fully independent experimental checks. A high-confidence complex that places a scrambled decoy on the same TNF patch may reveal model/selection bias rather than binding.
- Before using LocalFold results scientifically, a later authorized pilot would need to identify the actual deployed source/model/weight revision; establish whether selected inference executes on local hardware; record all network destinations and optional MSA/template behavior; check model terms, seed/sampling controls and exported requests; then compare on the frozen public peptide panel. That pilot is **not performed or authorized by this note**. Model-specific cyclic/D support must be demonstrated, not inferred from a menu entry or generic modified-residue claim.
- For now, implement a clean file-import boundary for optional predicted coordinates/confidence/provenance rather than coupling the lab to the live website or embedding sequence submission. Prediction remains a secondary hypothesis source; the HADDOCK3 pilot and benchmark gates come first.

### Gaps

- No local inference, browser network trace, model-specific weight inspection, numerical parity test, deployed-commit comparison, chemistry test or TNF complex benchmark was executed. The site footer and repository documentation are insufficient for an unconditional local-execution/privacy guarantee.
- No assertion is made that every menu entry has equivalent complex support, resource needs, reliability or licensing. This bounded engine review deliberately leaves those as optional-model gates.
